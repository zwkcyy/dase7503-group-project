## 1. 更新和构建

已有仓库且没有未保存改动时，在仓库根目录执行：

```bash
git fetch origin

git pull --ff-only origin codex/ec-hardware-integration

```

已经安装完整依赖时可以跳过 `install`。默认编译目录是 `~/dase7503-nav-work`，
源码仍在当前仓库；如需改编译目录，先设置 `NAV_WORKSPACE`，后续 source 使用同一个目录。
构建包列表已加入 `ec_serial_bridge`，`robot_bringup` 也已声明依赖。
不要从原来的仿真工作区启动旧版本通信节点。

## 2. 每个终端使用相同环境

```bash
source /opt/ros/jazzy/setup.bash
source ~/dase7503-nav-work/install/setup.bash
export ROS_DOMAIN_ID=76
export ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST
```

本步骤所有命令都在同一台主机执行（可以开多个 SSH 终端）。域 76 用于这次联调，
避免接入此前域 75 的仿真、假升降和演示节点。需要跨主机 ROS 通信时再统一调整发现范围。

查看实际串口：

```bash
ls -l /dev/serial/by-id/
ls -l /dev/ttyACM* /dev/ttyUSB*
```

某一种设备名不存在时出现提示是正常的。优先使用实际存在的 `/dev/serial/by-id/...` 完整路径。
下面以 `/dev/ttyACM0` 举例；USB 转串口也可能是 `/dev/ttyUSB0`，按实际替换。
若提示权限不足，将用户加入 `dialout` 后重新登录：

```bash
sudo usermod -aG dialout "$USER"
```

## 3. 先启动只接收数据的通信链路

终端 A，在仓库根目录执行并保持运行：

```bash
bash scripts/nav.sh ec start_bridge:=true port:=/dev/ttyACM0 baudrate:=115200 enable_motion:=false enable_lift:=false
```

默认会加载新桥配置 `ec_bridge_20261102.yaml` 和新适配配置 `ec_20261102.yaml`。
不会自动使能底盘，也不会自动启动导航。需要同时显示 CAD 时，可将 `ec` 换成 `hardware`，
但不要同时启动两个通信桥占用同一个串口。

终端 B，先执行第 2 节环境命令，然后分别查看：

```bash
ros2 topic echo /ec_bridge/status --once
ros2 topic echo /ec_adapter/status --once
ros2 topic echo /ec/lift_state --once
ros2 topic echo /odom/wheel --once
ros2 topic echo /imu/data_raw --once
```

预期：

- 桥状态 `open=true`、`link_ok=true`，接收帧计数持续增加。
- `ec_fault=0`；`ec_armed`、`ec_estop` 来自有效 84 状态帧。`null` 表示尚未收到或已过期，不能当成正常状态。
- 适配层 `telemetry_ready=true`，`lift_completion_source=ec_timed_state_transition`。
- `/ec/lift_state` 持续报告 0 或 1，实际机构位置应与其对应。静止时轮速和角速度应接近零。
- `motion_enabled=false`、`lift_enabled=false` 是这一阶段的预期值。

`last_ack` 表示最后一个回执，不是所有指令的综合状态。服务返回 `frame sent` 仅表示写入串口成功，
使能是否生效应查看 84 的 `ec_armed`；不要把服务返回值当成实车已经执行的证明。

## 4. 单独联调升降

先确认空载机构有完整行程空间、实际初始位置与反馈一致，再在终端 A 按 Ctrl+C，重新启动：

```bash
bash scripts/nav.sh ec start_bridge:=true port:=/dev/ttyACM0 baudrate:=115200 enable_motion:=false enable_lift:=true
```

等状态流恢复。终端 B 使能 EC：

```bash
ros2 service call /ec_bridge/set_arm std_srvs/srv/SetBool '{data: true}'
ros2 topic echo /ec_bridge/status --once
```

继续操作前应看到 `ec_armed=true`、`ec_estop=false`、`ec_fault=0`。
若 EC 报急停，先处理实际原因；本说明不自动释放急停。

终端 C 执行环境命令后，持续观察任务侧反馈：

```bash
ros2 topic echo /lift_state
```

若当前底端反馈为 0，在终端 B **只发送一次**上升：

```bash
ros2 topic pub --once /lift_cmd std_msgs/msg/Int8 '{data: 1}'
```

终端 C 应先出现 `-1`（本次请求尚未完成），收到 F0 接受回执、EC 状态从 0 变为 1 后，才出现 `1`。
EC 说明的行程时间约为 3 秒；树莓派不会仅根据三秒计时生成完成信号。
等实际机构停止且收到 `1`，再发送一次下降：

```bash
ros2 topic pub --once /lift_cmd std_msgs/msg/Int8 '{data: 0}'
```

应先收到 `-1`，再在 EC 状态从 1 变为 0 后收到 `0`。如果初始已经在顶端，应先下降。
已经位于目标端点时，重复同向命令会被拒绝，因为没有新的状态变化可以证明本次动作完成。
不要使用持续发布升降指令的命令，也不要在升降中交替发送上下指令。

查看拒绝或超时原因：

```bash
ros2 topic echo /ec_adapter/status --once
ros2 topic echo /ec_bridge/status --once
```

正常完成后，`lift_result` 会说明本次请求由 F0 接受和端点状态变化完成。
`lift_acknowledged` 仅描述当前尚未结束的请求，完成后为 false。
若 EC 不回 F0、只回旧端点、反馈中断、报故障或解除使能，本实现不会假报完成。
无回执时默认最多重发 5 次，且首帧后最多 2 秒；适配器等待完成最多 7 秒。

## 5. 停止与断线恢复的含义

```bash
ros2 service call /ec_adapter/stop_lift std_srvs/srv/Trigger '{}'
```

当前 `enable_lift_stop=false`，预期返回 `success=false` 并说明 EC 不支持 07。
服务、文本 `lift stop` 和枚举 2 都不会发送 07；待重发指令会取消，但这**不代表机械升降中途停止**。
已开始的升降可能继续走完剩余行程。05/04 对升降动力的实际影响仍取决于实板固件。

断线、重连、有效上行超时、停止、急停、解除使能、任务结束或显式取消都会清除旧待发指令。
恢复连接只请求状态，不自动使能、不重放旧升降；重新观察实际位置和新鲜反馈后，再发新命令。
断线与急停行为的实测应在空载机构有安全行程条件下进行，并记录实际执行器反应。

结束时，待机构静止后解除使能，再关闭终端 A 的启动进程：

```bash
ros2 service call /ec_bridge/set_arm std_srvs/srv/SetBool '{data: false}'
```
